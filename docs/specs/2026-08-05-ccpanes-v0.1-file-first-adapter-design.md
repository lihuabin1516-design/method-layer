# CC-Panes v0.1 File-First Adapter Design

**Status:** 已于 2026-08-05 确认并完成本地 reference adapter 实现  
**Decision:** 采用方案 A：文件优先的薄 Adapter  
**Protocol:** CC-Panes Method Layer `0.1`  
**Reference CC-Panes source:** `D:\cc-pane\.source\cc-pane` at `e63d0889c52b6f8dc1109266563327da59eb080e`

## 1. 目标与边界

Adapter 在 CC-Panes Orchestrator 与 v0.1 方法层 artifact 之间完成显式映射：

```text
task.json
  -> launch adapter
  -> CC-Panes launch_task / TaskBinding
  -> run.json
  -> finish adapter
  -> evidence.json
  -> handoff adapter
  -> handoff.json
```

设计遵循以下边界：

- `task`、`run`、`evidence`、`handoff` 文件是方法层事实源。
- TaskBinding 保存运行索引、会话状态和 artifact 引用。
- CC-Panes 的 pane、session、profile、runtime 与布局仍由 Orchestrator 管理。
- v0.1 `riskMode` 保持 advisory-only；profile 与 runtime 由调用方显式选择。
- `completionSummary` 是完成输入之一，不等同于验证证据。
- `handoff.nextOrder` 只表达后续门禁顺序，不触发下一次 launch。
- 本设计不要求修改 CC-Panes core、数据库、Tauri、REST、MCP 或 UI 类型。

## 2. 权威契约依据

本设计按以下 CC-Panes 源码契约建立：

| 契约 | 权威源码 |
| --- | --- |
| `launch_task` 请求、响应和 session 创建 | `src-tauri/src/services/orchestrator_service.rs` |
| TaskBinding 数据模型、状态和角色 | `cc-panes-core/src/models/task_binding.rs` |
| TaskBinding metadata merge-patch | `cc-panes-core/src/services/task_binding_service.rs` |
| 前端 TaskBinding 类型 | `web/types/orchestrator.ts` |
| TaskBinding service 调用 | `web/services/taskBindingService.ts` |

当前已确认：

- `launch_task` 使用 `projectPath`，并接受 prompt/resume、CLI、profile、provider、runtime、workspace 和布局参数。
- MCP 启动响应提供 launch-status `taskId`、`sessionId`、`status`、`runtimeKind`、`runtimeSource`、nullable `profileId` 和 nullable `notice`。
- `launch_task.taskId` 不是 TaskBinding identity；transport 使用 `sessionId` 调用 `find_task_binding_by_session`，必要时再创建或注册 binding。
- TaskBinding 状态为 `pending | running | waiting | completed | failed`。
- TaskBinding 角色为 `task | leader | worker`。
- TaskBinding `metadata` 支持深合并；单次 patch 上限为 64 KiB，合并深度上限为 16。
- worker 完成链路可先持久化 TaskBinding，再通过 `report_to_leader` 通知 leader；`reconcile_plan_collaboration` 用于重新读取持久化状态。

## 3. Artifact 存储布局

### 3.1 默认根目录

v0.1 adapter 使用项目内显式根目录：

```text
<projectPath>/.ccpanes-method/v0.1/
```

该目录与 CC-Panes 宿主状态目录 `.ccpanes/` 分离。adapter 每次操作都接收或解析明确的 `projectPath`，不依赖用户全局配置。

### 3.2 任务目录

```text
.ccpanes-method/v0.1/
  tasks/
    <task-key>/
      task.json
      runs/
        <run-key>/
          run.json
          evidence/
            <evidence-key>.json
      handoffs/
        <handoff-key>.json
  adapter/
    launch-attempts/
      <attempt-key>.json
```

其中：

- `task.json` 是 task identity、授权和验收的权威文件。
- `run.json` 记录一次具体 CC-Panes session 绑定。
- `evidence/*.json` 采用追加式写入；已有 evidence identity 不被静默覆盖。
- `handoffs/*.json` 采用追加式写入。
- `adapter/launch-attempts/*.json` 是短期操作日志，不属于四类协议 artifact。

### 3.3 Windows 路径编码

schema 允许 `taskId` 等 identity 包含 `:`，原始值不直接作为 Windows 路径段。adapter 对路径段使用 UTF-8 percent-encoding：

- `[A-Za-z0-9._-]` 保持原样。
- 其它字节使用大写 `%HH`。
- artifact 文件内继续保存原始 identity。

例：

```text
taskId: team:task-001
task-key: team%3Atask-001
```

解析后的绝对路径必须位于 `<projectPath>/.ccpanes-method/v0.1/` 内。adapter 检查 `..`、绝对路径注入、符号链接和 junction 越界。

## 4. 文件一致性模型

### 4.1 写入规则

每次 artifact 写入按以下顺序执行：

1. 在目标目录创建同卷临时文件。
2. 写入 UTF-8 JSON。
3. 运行 JSON 语法和对应 schema 校验。
4. 计算 SHA-256。
5. 使用原子 rename/replace 发布目标文件。
6. 重新读取目标文件并复核 SHA-256。
7. 再更新 TaskBinding 引用。

TaskBinding 更新失败时，artifact 文件仍是事实源；后续 reconcile 可按 `sessionId`、`runId` 或目录扫描恢复引用。

### 4.2 并发与覆盖

- task 与 run 更新携带调用方读取到的 `expectedSha256`。
- 当前文件 SHA-256 与预期值不一致时，adapter 返回 `conflict`，保留双方文件。
- evidence 与 handoff 采用 create-once identity；同 identity 的第二次写入只有在内容 SHA-256 完全一致时视为幂等成功。
- per-task 锁文件位于 task 目录，锁只覆盖一次本地事务，不跨 worker 执行周期持有。
- 锁记录 owner、PID、createdAt 和 operation；过期锁进入人工或显式 recovery 流程。

## 5. TaskBinding 最小映射

### 5.1 metadata 结构

TaskBinding 只保存小型、可重建的引用：

```json
{
  "methodLayer": {
    "protocolVersion": "0.1",
    "taskId": "task-example-001",
    "runId": "run-example-001",
    "artifactRoot": ".ccpanes-method/v0.1",
    "taskPath": "tasks/task-example-001/task.json",
    "runPath": "tasks/task-example-001/runs/run-example-001/run.json",
    "latestEvidencePath": "tasks/task-example-001/runs/run-example-001/evidence/evidence-example-001.json",
    "latestHandoffPath": "tasks/task-example-001/handoffs/handoff-example-001.json"
  }
}
```

约束：

- 路径相对 TaskBinding `projectPath`，统一使用 `/`。
- `latestEvidencePath` 和 `latestHandoffPath` 只表示索引，不改变历史文件。
- metadata 不嵌入完整 artifact、命令输出、补丁、日志或密钥。
- adapter 只 patch `metadata.methodLayer`，保留其它 metadata namespace。
- 正常 patch 目标控制在 8 KiB 内，为 CC-Panes 64 KiB 上限留出余量。

### 5.2 字段职责

| TaskBinding 字段 | Adapter 用法 |
| --- | --- |
| `id` | CC-Panes binding identity，写入 launch attempt 和 recovery 日志 |
| `parentId` / `role` | leader/worker 关系；不替代 method `taskId` |
| `sessionId` / `resumeId` | 映射到 `run.runner.session` |
| `projectPath` / `workspaceName` | 与 task baseline、run workspace 交叉校验 |
| `cliTool` | 映射到 `run.runner.cliTool` |
| `status` / `progress` | CC-Panes 执行状态；与 evidence outcome 分开解释 |
| `completionSummary` | evidence 候选摘要输入 |
| `exitCode` | finish 事实输入，可写入 check notes 或 adapter 日志 |
| `metadata.methodLayer` | 协议版本、method identity 与 artifact 路径索引 |

## 6. Launch Adapter

### 6.1 输入

- task artifact path
- 显式 `cliTool`
- 显式 profile/provider/runtime 选择
- 可选 workspace、pane、layout、placement
- 可选 resume identity
- artifact root

### 6.2 前置门禁

产生 CC-Panes 副作用前依次检查：

1. task JSON 语法与 `task.schema.json`。
2. `protocolVersion` 精确等于 `0.1`。
3. task artifact 路径位于 artifact root。
4. `task.baseline.projectPath`、`repoRoot` 与实际解析路径一致。
5. Git branch、HEAD、status 与 task baseline 的声明一致，或由调用方显式重新基线化 task。
6. 当前动作位于 `authorization.allowedPaths`，且未命中 `forbiddenActions`。
7. conditional action 已附带本轮明确批准证据。
8. `cliTool`、profile、runtime 来自显式输入；不从 `riskMode` 推导。

任一门禁不满足时，launch 调用保持未执行状态，并返回结构化诊断。

### 6.3 Prompt 渲染

launch prompt 由固定段落组成：

1. method task identity 与 artifact 路径
2. objective
3. authorization 与 conditional approvals
4. baseline 与 applicable rules
5. acceptance 与 required evidence
6. stop conditions
7. run/evidence 写入约定
8. worker completion reporting 顺序

prompt 是 task 内容的执行投影。授权、验收和停止条件保持原义，adapter 不扩写权限。

### 6.4 启动事务

由于 `run.schema.json` 要求真实 `sessionId`，run artifact 在 `launch_task` 成功响应后发布。启动事务使用内部 attempt 日志：

```text
prepare attempt
  -> validate task and inputs
  -> persist attempt(state=prepared)
  -> call launch_task
  -> persist response(state=launched)
  -> build and validate run.json
  -> publish run.json
  -> patch TaskBinding metadata
  -> persist attempt(state=bound)
```

attempt 至少记录：

- attempt identity
- method `taskId` 与预分配 `runId`
- task path 与 task SHA-256
- launch 参数摘要
- launch response 的 TaskBinding/session identity
- 当前状态与最后错误

attempt 不复制 prompt 全文和 task 全文。

### 6.5 run 映射

| run 字段 | 来源 |
| --- | --- |
| `runId` | adapter 在 launch 前分配 |
| `taskRef` | task identity、版本和相对路径 |
| `startedAt` | launch 请求开始时间 |
| `status` | launch 成功后为 `running`；恢复场景按实际状态映射 |
| `runner.cliTool` | launch 显式输入 / TaskBinding 实际值 |
| `runner.profile` | 实际 profile identity；无 identity 时使用稳定的显式 display value |
| `runner.runtimeKind` | launch response 的实际 runtime |
| `runner.session.sessionId` | launch response |
| `runner.session.resumeSessionId` | resume 输入存在时写入 |
| `workspace.projectPath` | 规范化后的 task baseline / launch projectPath |
| `workspace.worktreePath` | 实际执行 worktree |
| `workspace.branch` | launch 时重新读取 |
| `contract` | task objective、authorization、acceptance、requiredEvidence、stopConditions 的深拷贝快照 |

`run.contract` 发布后保持 launch-time snapshot 语义。task 后续更新通过新 run 体现。

## 7. Finish 与 Evidence Adapter

### 7.1 状态分层

CC-Panes TaskBinding 状态描述 session/binding 执行状态；method evidence 描述目标与验收结果。两者保持独立：

| CC-Panes 状态 | Method 层解释 |
| --- | --- |
| `pending` / `running` / `waiting` | run 尚在进行 |
| `completed` | worker/session 已完成报告，仍需 evidence gate |
| `failed` | worker/session 执行失败，evidence 仍记录已发生事实 |

TaskBinding `completed` 不自动生成 `evidence.outcome = completed`。

Reference adapter 的 `finish-run` 保留输入 TaskBinding 的 `status` 与 `progress`；执行状态迁移属于 runtime/transport。method outcome 只写入 run/evidence 与返回 envelope 的 `methodOutcome`。

### 7.2 Evidence 输入

finish adapter 合并以下输入：

- task artifact
- run artifact
- worker 生成的 evidence draft 或完整 evidence
- TaskBinding `completionSummary`、`exitCode`、session identity
- fresh Git status
- 实际执行的 required/optional checks
- scope、files、acceptance drift assessment

若只有 `completionSummary`，adapter 生成待审 evidence draft：

- summary 取 completion summary
- 未执行检查记录为 `not-run` 或 `blocked`
- drift 使用 `needs-review`
- outcome 使用与证据相符的 `partial`、`blocked` 或 `failed`

adapter 不把摘要推断成测试通过、文件清单或完成结论。

### 7.3 Finish 顺序

worker 路径按以下顺序：

1. 收集并发布通过 schema 的 evidence。
2. 更新 run 的 `endedAt` 与 method 对应状态。
3. `update_task_binding` 持久化 status、progress、completionSummary、exitCode 和 methodLayer 引用。
4. `report_to_leader` 发送简短通知。
5. leader 需要恢复时使用 `reconcile_plan_collaboration` 读取持久化状态。

通知队列只承担提示作用。artifact 与 TaskBinding 持久化完成后，leader 通知丢失仍可恢复。

### 7.4 完成门禁

method outcome 进入 `completed` 需要同时满足：

- task objective 与 run.contract 一致。
- 所有 required checks 为 `pass`。
- 每个 `task.requiredEvidence` 都有同名、`required: true`、`status: pass` 的 evidence check。
- driftCheck 的 scope、files、acceptance 均为 `aligned`。
- touchedFiles 对所有实际创建、修改、删除和关键检查路径有解释。
- Git 状态符合 task authorization。
- residual risk 与 recommended next action 已填写。

未满足的项目以真实状态进入 evidence，不通过修改 TaskBinding 状态掩盖。

## 8. Handoff Adapter

handoff adapter 读取：

- 当前 task 与 run
- 最新有效 evidence
- 当前项目/Git baseline
- applicable `AGENTS.md`
- 当前授权、条件授权和停止条件
- leader/worker 持久化状态

生成流程：

1. 重新读取 task、run、evidence 并校验 SHA-256 与 schema。
2. 重新采集 current baseline。
3. 按 `handoff.schema.json` 生成九段式 artifact。
4. 校验 requiredReading、requiredChecks、acceptanceAssertions 和 stopConditions 非空。
5. create-once 发布 handoff。
6. patch TaskBinding `latestHandoffPath`。
7. 返回 handoff path 和 SHA-256。

handoff adapter 只生成控制契约。后续 controller 重新验证 artifact 后，再作 launch 决策。

## 9. 恢复矩阵

| 故障点 | 权威状态 | 恢复动作 |
| --- | --- | --- |
| task 校验失败 | task 文件与诊断 | 修正或重新生成 task，再次校验 |
| attempt 已准备，launch 未返回 | attempt `prepared` | 查询 launch history/TaskBinding；确认无 session 后显式重试 |
| launch 成功，run 发布失败 | attempt `launched` + response identity | 用记录的 session/TaskBinding 重建 run |
| run 已发布，metadata patch 失败 | run 文件 | 按 sessionId 查 TaskBinding并补写引用 |
| evidence 发布失败 | 原 run 与 draft | 保留 draft/诊断，重新收集 fresh evidence |
| TaskBinding 已完成，evidence 缺失 | TaskBinding + run | 生成 partial/blocked evidence，进入审阅 |
| leader 通知丢失 | TaskBinding + artifact | reconcile 后读取 methodLayer 引用 |
| handoff 发布失败 | task/run/evidence | 保持现有 artifact，修复后重新生成新 handoff identity |

重试必须幂等：相同 identity 与相同 SHA-256 成功，相同 identity 与不同内容返回 conflict。

## 10. 版本与兼容策略

- adapter v0.1 只消费 `protocolVersion: "0.1"`。
- schema `$id` 与 artifact `protocolVersion` 同时校验。
- 未识别版本在任何 launch/finish/handoff 副作用前返回版本诊断。
- metadata 使用顶层 namespace `methodLayer`，其内部版本字段用于路由。
- 新增协议版本使用并列目录和 schema，不原地改变 v0.1 语义。
- CC-Panes 字段发生变化时，先更新 contract fixture 与映射测试，再调整 adapter。

## 11. 安全与审计约束

- 所有写入路径先 canonicalize，再验证位于 artifact root。
- 路径检查覆盖 Windows junction、symlink、UNC 和大小写归一化。
- artifact 与 metadata 不记录 token、密钥、完整环境变量或生产数据。
- prompt 中只放执行所需的 task 内容和相对 artifact 引用。
- 每次 adapter 操作输出 operation id、输入 artifact SHA-256、输出 artifact SHA-256 和 CC-Panes binding/session identity。
- `riskMode`、profile、TaskBinding role 和 completion summary 均不扩展 authorization。
- merge、push、cleanup、远端写入和用户配置写入继续由 task authorization 独立门禁。

## 12. 实现分层建议

未来 adapter 可保持四层：

```text
commands/
  launch
  finish
  handoff
domain/
  schema validation
  artifact mapping
  state transitions
storage/
  path containment
  atomic JSON writes
  SHA-256 / conflict detection
ccpanes/
  launch_task
  TaskBinding patch/query
  report/reconcile
```

domain 与 storage 可在无 CC-Panes runtime 的条件下测试；`ccpanes/` 通过窄接口注入。

## 13. 验收断言

实现阶段至少证明：

1. invalid task 在 launch side effect 前被拒绝。
2. raw identity 中的 `:` 不直接进入 Windows 路径段。
3. 路径遍历、symlink 和 junction 越界被拒绝。
4. `riskMode` 的不同取值不改变 profile/runtime 选择。
5. run.contract 与 launch 时 task 约束字段完全一致。
6. launch 成功且 run 写入失败时，可从 attempt 日志恢复。
7. TaskBinding metadata 不包含完整 artifact，正常 patch 小于 8 KiB。
8. metadata patch 保留其它 namespace。
9. 只有 completion summary 时，evidence 不产生虚构 pass。
10. required check 非 pass 或 drift 非 aligned 时，method outcome 不进入 completed。
11. evidence 在 TaskBinding 更新和 leader 通知之前发布。
12. leader 通知丢失后，可通过 reconcile 与 artifact 引用恢复。
13. handoff 通过 schema 且九段式必填内容均存在。
14. handoff 生成不触发下一任务。
15. v0.1 schema、valid/invalid examples 与现有验证脚本继续全部通过。

## 14. 当前决策与后续门禁

本设计冻结以下决定：

- 文件是方法层唯一事实源。
- TaskBinding metadata 只保存引用。
- 使用 project-local `.ccpanes-method/v0.1`。
- 自定义 project-local artifact root 由 `run.taskRef.artifactPath` 推导并贯穿 finish/handoff。
- launch 使用短期 attempt 日志解决 session 创建与 run 发布之间的事务间隙。
- finish 先发布 evidence，再更新 TaskBinding，再通知 leader。
- handoff 只生成 artifact。
- CC-Panes 原生模型和数据库保持现状。

实施计划位于 `docs/plans/2026-08-05-v0.1-file-first-adapter.md`。PowerShell 7 reference adapter、内部 schemas、恢复链路和 dependency-free tests 已实现；CC-Panes runtime transport 仍作为后续独立门禁。
